# 方案 A：静态优先管道（守序渐进）

沿 v1 的静态事实路线做实，补上规范化 IR、沙箱、事务分类三个缺口。设计底线：**管道永不因项目状态异常而中断，只降级**。每个阶段声明自己的失败分支和降级产物——这是"数据流能否跑起来"的答案所在。

## 数据流总览

```
源码目录
  │
  ▼
[Stage 0] 预检 precheck ──→ capability-manifest.json
  │   检查: git? 构建系统? 入口? 测试? 密钥? 副作用线索?
  │   失败分支: 无 git → 自动 init + 初始 commit
  │             无法识别构建 → 标记 degraded，跳过 Stage 4 执行
  ▼
[Stage 1] 事实基座 index ──→ facts.db (SQLite，自有 schema)
  │   失败分支: 解析失败文件 → 记录为 opaque 节点，不丢弃
  ▼
[Stage 2] 语义增强 ──→ 写回 facts.db，每条边带证据等级
  │   失败分支: LSP 不可用 → 启发式地板 (family-gated)
  ▼
[Stage 3] 规范化 IR（自建核心）
  │   canonical ID 铸造: file path + qualified name + content hash
  │   证据等级序: dynamic > lsp-exact > family-gated > heuristic
  ▼
[Stage 4] 行为冻结 freeze
  │   车道 A (可运行): 沙箱内生成表征测试并执行 → freeze pack
  │   车道 B (不可运行): 仅静态冻结 (IR 快照)，行为闸门整体降级
  ▼
[Stage 5] dossier 生成（视图生成器）
  │   按 token 预算产出分层视图: 模块地图 / 函数卡片 / 问题清单
  ▼
[通用 AI 消费] 语义摘要 / grill 问卷（默认自答+置信度）/ 事务草案
  │
  ▼
[Stage 6] 事务执行 transact
  │   每个事务: 编辑脚本 + 预期结构 delta + 事务类型
  │   事务内: 执行 → 重扫 → 闸门 → commit 或 rollback (git)
  ▼
[Stage 7] gate ──→ verdict.json（证据强度分级，非二值证明）
```

## 重构事务分类学（v1 缺失的核心）

v1 的统一闸门"行为等价 ∧ 结构改善"隐含假设所有重构都是等价重构。vibe 项目的实际诉求一半以上不是等价重构。按事务类型分派闸门：

| 类型 | 例子 | 行为闸门 | 结构闸门 | 自动化 |
|---|---|---|---|---|
| T1 等价重构 | 移动/重命名/提取函数 | 表征测试通过 + 差分 fuzz | delta 与声明一致 | 全自动 |
| T2 清理 | 删死代码/死依赖 | 表征测试通过 | 引用完整性，无悬空引用 | 全自动 |
| T3 修复 | 补依赖/修入口/修构建 | 不适用（行为本就不存在） | 可运行性单调改善：前 broken 后 runs | 自动，产物标记"非等价变更" |
| T4 改进 | 改逻辑/改 API 契约 | 新表征测试（描述目标行为） | 契约 diff 显式化 | 需确认 |

要点：T3 是 vibe 项目最常见的第一步（"先让它跑起来"），在 v1 的闸门下永远非法——这是 v1 逻辑上跑不通的根源。等价性只在 T1/T2 有定义。

## 降级模式矩阵

预检结果决定管道走哪条车道，车道决定闸门强度：

| 预检发现 | 车道 | 行为证据 |
|---|---|---|
| 可运行 + 有测试 | 全速 | 存量测试 + 表征 + fuzz |
| 可运行 + 无测试 | 标准 | 生成的表征测试 |
| 可运行但缺外部密钥 | 标准-回放 | record/replay mock 外部 API |
| 不可运行 | 结构 | 仅静态；T1 行为闸门降级为"引用完整性 + 导入可解析" |
| 无法识别构建 | 最小 | 仅 Stage 1-3；只产出 dossier，不执行事务 |

## 关键设计决策

1. **单一事实源**：facts.db 用自有 schema，上游工具（codebase-memory-mcp 等）只是可替换的 provider。工具停更换 provider，schema 不动。
2. **图匹配用事务声明解决**：不做图同构。每个事务声明"移动了什么"（旧 ID → 新 ID 映射），闸门按声明验证；未声明的结构差异一律视为回归。把不可判定问题变成工程问题。
3. **行为等价不可判定**：闸门输出证据强度分级（表征覆盖率 / 测试通过率 / fuzz 结果 → 高/中/低置信 verdict），阈值可配，不承诺证明。
4. **全量重扫作为基线**：vibe 项目千行级，每事务全量重扫是秒级操作。增量索引是后期优化，v1 不做。
5. **执行沙箱是 Stage 4 的硬前提**：容器/VM、网络隔离、文件系统快照。表征测试生成会执行任意代码，不沙箱不可上线。
6. **批处理模式优先**：grill 问卷默认由消费者 AI 自答并标注置信度，管道永不等待交互；人工确认是可选增强，不是依赖。

## 与 v1 的差异

- 新增 Stage 0 / 规范化 IR 层 / dossier 视图生成 / 执行沙箱
- 验证从"第四层的一个步骤"改为每事务一个闸门 + git 自动回滚
- 统一闸门拆为按事务类型的闸门矩阵
- 多源交叉验证（Unwind / tree-sitter-analyzer）移出生产管道，进离线 eval harness

## 风险与开放问题

- 表征测试自动生成对异步/并发/长连接代码的质量未知，需要 eval 集
- 沙箱在 Windows 宿主上成本高，优先 Docker，备选 WSL2
- LLM 产出的事务草案可能混型（一个事务里既有 T1 又有 T4）：事务格式强制单类型，混合草案自动拆分
- 缺密钥车道下，表征覆盖率与重构范围存在循环依赖（想删的代码恰好测不到）
