# schema 版本承诺（V18）

> 立项来源：构想v12 V18（只读 API 稳定化）；随批⑦（#205，BB1+V17）定稿。
> 本文档是 facts.db 表结构对第三方只读消费者的版本契约政策。

## 1. 版本机制

- facts.db 用 SQLite 原生 `PRAGMA user_version` 记录 schema 版本（当前 **2**）。
- `0` = pre-tracking 旧库（schema 版本机制引入前）——打开时探测并迁移，见 §3。
- 版本号只增不减；每次不兼容变更 +1。
- v1 为理论基线槽：从未有库真实处于 user_version=1（批⑦ D7 决策点记档——SCHEMA_VERSION=2 起步），迁移链从 0 直达 2，v1 槽保留给未来回溯测试用途，不代表历史发布版本。

## 2. v0.x 政策（宽松）

发布早期（v0.x）采用宽松政策：

- **破坏性变更随 minor 走**：v0.1→v0.2 可含破坏性 schema 变更——公开承诺=变更成本上升（反向风险，构想v12 V18 原文），早期宜轻装。
- **N-1 库可迁移承诺**：相邻版本旧库在当前代码下打开时自动迁移到当前版本（例：user_version=1 的库在 v2 代码下打开自动升级）。跨两版本及以上（N-2 及更早）不承诺自动迁移，诚实拒绝并提示重跑 ETL。
- **重建永远等价**：任何旧库均可通过重跑 ETL 从源仓重建（ETL 是唯一权威写入路径）——迁移是便利不是依赖；迁移结果与重建结果在行集语义上等价。

## 3. 迁移链工程规则

- 迁移以线性链组织：`vrp/etl.py` `MIGRATIONS: list[tuple[int, Callable]]`（学 alembic 线性链思想，零依赖自建）。
- 每个迁移必须**幂等**：重复执行无副作用（`PRAGMA table_info` 探测列存在性；空表清单跳过）。
- 视图引用新列时：**先 ALTER 表、后 executescript 重建视图**（`ensure_schema` 先迁移后建视图的硬约束——视图引用尚不存在的列会失败）。
- 每个迁移配套旧版库 fixture 测试：tests/test_migrations.py 迁移矩阵（新库版本/v0 升级/幂等/视图替换/半迁移探测/迁移链形状/迁移后写入面）。
- 写路径打开旧库时前置迁移（`cmd_s2` 等写命令 rw 连接先 ensure_schema）；只读消费者不迁移、不降级，按原样读取。

## 4. 反向风险记档

公开承诺=变更成本上升：本政策刻意收窄承诺面至「N-1 可迁移+重建等价」两条，不承诺字节级 schema 稳定，不承诺列清单冻结——v0.x 阶段列可增（append-only 倾向），旧列原则上不删；列删除或语义变更须伴随 user_version +1 与迁移。

## 5. 消费者指南（速览）

- 第三方只读消费 facts.db：读 `PRAGMA user_version` 判断兼容性；user_version 高于自身预期时不要臆测列含义。
- 只读连接请走版本探测而非硬编码列清单；未迁移旧行的 `resolution_label` 为 NULL（未知），与显式低置信值严格区分——NULL 不参与任何"必死"类判定（与 v_dead_code 语义一致）。
