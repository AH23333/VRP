## 二、管道改进项（由实测反哺）

### P-1 生成物/产物噪音是最大普遍问题（10/15 项目命中）

archify 生成的 HTML 图（7 个项目各 9–13 页、每页 358 符号、`viewerText` fan-in 52、页间相似 254）、构建产物入库（CookMyFridge `site/`、StarMarkDesktop 之外的多个 docs/_build）、压缩 vendor 库（digitaljs.js 5675、excalidraw.min.js 1944、tailwind.cdn 746）——**这些占了各项目 50%–98% 的索引符号**，且大量制造假 findings（similar_to 噪音主体）。

**改进**：S1 索引后增加"产物目录启发式检测"报告——对满足特征（页面符号数高度一致 358×N、`.min.js`/`-rendered.html`/`_build`/`dist/` 命名、同 hash 副本）的目录输出提示，建议用户排除；xcheck 对压缩 JS 的调用提取分歧（archify 项目 cbm_only 45083）可先按 `.min.js`/单行超长文件降权。

**已实施（P 批，commit 51）**：`etl.detect_artifact_noise` 四类规则（artifact_dir_name 子树聚合 / minified_or_dense / uniform_html_pages / same_hash_copies）→ `.vrp/artifact-hints.json` + `stats["artifact_hints"]`，提示永不自动排除；xcheck 对 `.min.js`/`.min.css`/`.min.mjs` 两侧对称排除，计数公开（`ca_minified_*`/`cbm_minified_*` 入 summary/meta）。单行超长检测需逐文件读内容，成本不成比例，未做（诚实边界）。dogfood：vrp 自仓检出 2 簇真实同 hash 副本（空 `__init__.py` 双份等）。

### P-2 非代码仓库识别缺失

HomeWork（6372 个 AI 生成内容文件）导致 CBM 按代码索引，超内存预算失败（budget 3583MB / peak 3988MB）。precheck 阶段若能按扩展名分布（JSON/HTML/PDF 占比 >90%、无构建系统、无源码入口）提前判定"内容仓库"，可直接给出"不适用"结论，省去一次大内存索引尝试。

**已实施（P 批，commit 51）**：`s0_precheck.content_repo_probe`（内容占比 >90% 且零源码文件且无构建系统标记，三条件缺一不可）入 `precheck.json`；`vrp run` 检出时跳过 S1/S1.5/xcheck 并打印结论（rc=0，单命令 `vrp index`/`vrp etl` 可手动绕过——提示非硬门）。

**实测修正（P 批 dogfood）**：HomeWork 真仓复验**不符合**"纯内容仓"签名——6310 文件中 `.js` 2043 个（几乎全部位于 `_build/shots/_prof_vue0/` 浏览器 profile 快照），内容占比仅 38.8%，probe 据实放行（零特调：不为命中而调规则）。HomeWork 实为"产物污染仓"，其正确工具是 P-1 hints（`_build` 在 artifact 段表内）+ CBM 内存保护（已正确工作）。新发现 gap：`_build` 不在 s0 `IGNORE_DIRS`（仅 `build`），census/probe 会深入 `_build`——**已实施（R-I 批，2026-11-10）**：`_build` 入 IGNORE_DIRS 后 HomeWork census 从 2043 `.js` 污染降为真实 13 个语言文件（md/json）；probe 判定不变（detected=False，share 74.3%<90%——根目录 9 个无扩展名 archify 备份拉低占比，保守阈值正确工作）。

### P-3 CBM 符号共享假象

archify 实测中 `test/joint-layout-contract.test.mjs` 的 `requestAnimationFrame` fan-in 1000，但该文件仅 329 行、真实 CALLS 37——CBM 对跨文件同名符号（浏览器全局桩）合并计数产生假热点。dossier 的 hotspots 视图可加"文件内调用占比"列辅助人工快速识别此类假象。

**已实施（P 批，commit 51）**：`v_hotspots` 增加 `fan_in_same_file` / `fan_in_same_file_pct` 两列（视图 DROP+CREATE 幂等重建，旧库下次打开自动获新列；dossier hotspots `SELECT *` 与 MCP 消费者自动透传）。vrp 自仓实证：top 热点 `tests.test_s2_astgrep.repo` fan_in=361 而同文件仅 1（0.3%）——CBM 跨文件同名合并（同名 `repo` fixture）假象立现。

### P-4 分析器环境三条实录（跨 cache 冲突谱系完整）

本轮分析实际遇到的环境事件链：Qoder CBM 会话冲突（R-G 已录）→ Qoder 关闭后活跃 daemon 切换到 `D:\cbm-cache`（screen-translator 首跑拒绝后对齐成功）→ HomeWork 内存预算保护。**CBM 单 daemon 跨 cache 硬拒的行为在真实工作流里高频出现**——建议上游（work/cbm-upstream-bug-report.md 已有底稿）补充"daemon cache 路径"到错误消息的 `requested cache` 一行旁，方便一眼对齐。

**已实施（P 批，commit 51）**：`work/cbm-upstream-bug-report.md` 增补第二条 issue 底稿——daemon cache 目录不匹配错误未含 daemon 实际 cache 路径，含期望文案（requested/daemon 双路径并列）与复现步骤。

### P-5 值得保留的正面信号

- similar_to 在生产代码内零误报（所有真发现——UI 窗口四胞胎、escapeHtml 双实现、CookMyFridge site/web 双轨、四项目假阳性均已被人工核实为真）；
- 单文件 6532 行（app.js）/11299 行（protocol.rs）级别的巨石均被符号分布+热点正确暴露。

**无需改动**：正面信号，行为保持。
