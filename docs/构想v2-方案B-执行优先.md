# 方案 B：执行优先（行为考古）

## 核心倒置

v1 和方案 A 都是"静态事实优先，执行作为验证手段"。方案 B 把顺序倒过来：**对可运行的项目，执行本身就是最硬的事实来源**。一个函数是否是死代码，静态分析只能说"没找到调用者"（可能是误报），一次带覆盖率的试运行直接给出证据。

vibe 项目画像恰好有利：大多是 web 服务/脚本，有明确入口，一跑就知生死。

证据等级重排（与方案 A 的关键差异）：

```
executed (动态) > lsp-exact > family-gated > heuristic
```

## 数据流

```
[Stage 0] precheck ──→ 同方案 A
  ▼
[Stage B1] 试运行 probe（沙箱内）
  │   安装依赖 → 启动 → 探活；失败则采集报错栈
  │   失败分支: 报错栈喂给 LLM → 生成 T3 修复事务 → 重试，上限 N 次
  │             N 次仍失败 → 回退方案 A 的"结构车道"
  ▼
[Stage B2] 驱动生成（LLM）
  │   读入口/路由/CLI 定义，生成探索脚本（curl 序列 / Playwright / CLI 调用）
  │   产出: driver pack + 每条驱动的预期输出
  ▼
[Stage B3] 流量录制
  │   driver 执行 × coverage instrumentation × HTTP record/replay
  │   外部 API 密钥缺失 → mock 层以录制/合成响应顶替，请求结构仍被验证
  │   产出: trace.db（执行轨迹 + 覆盖率 + 录制的响应）
  ▼
[Stage B4] 表征 harness 固化
  │   driver + 录制回放 固化为可重跑测试套件 = freeze pack
  │   这套 harness 是第一个交付物，先于任何重构发生
  ▼
[Stage B5] 静态 IR（辅助地位）
  │   同方案 A 的 Stage 1-3，但边权按 trace 校正:
  │     静态有边 + trace 走到        → confirmed
  │     静态有边 + trace 从未走到    → cold（候选死代码，非死代码）
  │     静态无边 + trace 走到（动态派发）→ 补边，证据 = executed
  ▼
[Stage B6] 事务与闸门：同方案 A，但 T1/T2 的行为闸门直接跑 harness
```

## 杀手级能力

**基于执行证据的死代码识别。** "重构后删掉 40% 代码且行为不变"对 vibe 项目是最高价值主张，而静态死代码检测误报率高（反射/动态加载/入口点误判）。trace 校正后的 cold 集合，加上显式免责声明（"这些入口未被 driver 覆盖，删除前提是扩展 driver"），是静态优先方案给不出的证据质量。

**T3 修复有了自然路径。** probe 的报错栈就是修复事务的输入。"先让它跑起来"不再是非等价变更的例外处理，而是管道的常规第一阶段。

## 与方案 A 的关系

不是竞争，是分层：B 复用 A 的 Stage 3 之后全部实现，差别只在事实来源优先级和 B1-B4 的前置。**A 是 B 不可运行时的回退车道**。

## 风险

- **driver 生成的质量决定一切**：探索不到的路径 = 无动态证据，会系统性高估死代码。driver 覆盖率必须在 dossier 中显式报告，cold 集合默认不可自动删除。
- 有副作用的代码（发邮件/写库）在沙箱内执行需要网络白名单 + 合成响应，工程量集中在 B3。
- 长驻进程/定时任务/cron 类项目的 driver 形态不同。v1 只支持 req/resp 型（web/api/cli），其余走方案 A。
- 录制回放的脆性：上游 API 响应格式漂移会误报行为变化，freeze pack 需要响应结构归一化（只锁定 schema + 关键字段，不锁全量字节）。
