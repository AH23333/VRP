下面把整个对话中逐步形成的方案整理成一份完整、可执行的综合方案。它不是对某个工具的推荐，而是一套**分层架构 + 工具映射 + 组装原则**，每一层都标注了可复用的现成组件和需要自己补的缺口。

# 综合方案：面向通用 AI 的 vibe 项目重构分析管道

## 核心设计原则

**1. 事实层与 LLM 层彻底解耦。** 所有工具产出的都是结构化数据（JSON、SQLite、知识图谱），LLM 作为独立消费者接入，不绑定任何 Agent 的插件机制。Unwind 的 Claude Code 外壳、MCP 的协议形态，都是可替换的“交付形态”，不是方案的组成部分。

**2. 语言覆盖取并集，证据等级显式标注。** 语法事实对宽口径语言开放（158 种），语义精度对窄口径语言做深（9–13 种），每条边必须携带 `LSP-exact` / `family-gated` / `启发式匹配` 的证据等级。LLM 对低证据等级的边必须标记为待验证假设。

**3. 分层 IR，不追求单一 schema。** 静态结构、语义/运行时、业务语义三层各有独立 schema 和提取管道，层间通过节点 ID 锚定。

**4. 验证闭环不可跳过。** 重构后必须同时证明“结构改善”和“行为未变”，前者用结构差异对比，后者用表征测试或差分执行。

---

## 分层架构与工具映射

### 第一层：语法事实基座（宽语言覆盖，确定性）

**目标**：产出跨语言统一的符号清单、导入图、AST 结构，作为一切上层分析的 ground truth。

**主选工具**：
- **`codebase-memory-mcp`**：tree-sitter 编译进单一二进制，覆盖 **158 种语言**，零依赖，索引速度极快（Linux 内核 2800 万行约 3 分钟）。知识图谱以 **SQLite 持久化**，支持 `--json` 输出完整结果信封，也可导出 zstd 压缩的图数据库工件。**与 AI 平台解耦的关键**：LLM 层不需要是 MCP 客户端，直接读 SQLite 或 JSON 文件即可。
- **`Unwind` 的 `@unwind/core`**：基于 tree-sitter 的确定性扫描器，产出 **`scan-manifest.json`**（文件清单、结构符号、导入图、第一遍分层分配），明确标注为“确定性中间产物”。符号级覆盖 **TS/JS、Python、Rust、Java、C#** 五种语言，其余语言文件级覆盖。**用途**：在这 5 种语言上作为第三源交叉验证，与主图谱做一致性比对。

**质量校验器**：
- **`tree-sitter-analyzer`**：完整调用图覆盖 **13 种语言**，另有 8 种符号索引级。独特价值是 **family-gated call graph**，专门防止跨语言名称误连（HuggingFace tokenizers 测试中，名称匹配解析器错连 1,259 条边，它错连为 0）。**用途**：不担任主索引，作为调用图边的抽样校验器，把可疑边降级为“启发式”等级。输出格式 TOON（比 JSON 更紧凑）。

**产出形态**：SQLite 知识图谱 + JSON 事实导出 + `scan-manifest.json`（交叉验证源），全部 UTF-8 编码，节点带精确行列/字节偏移。

---

### 第二层：语义增强（按需，绑定语言服务器）

**目标**：在语法骨架上填充精确的跨文件引用、类型关系、调用层次。

**主选工具**：
- **`code-atlas`**：索引 **25 种语言**，设计原则是“**LSP-exact answers with a structural floor**”——语言服务器可用时返回精确答案（标记 `[lsp 1.00]`），不可用时回退到结构化索引，名称匹配只作为候选。提供 32 个工具，覆盖调用/类型层级、导入图、变更影响分析、Web 框架路由图，持久化在 SQLite，每次查询有 token 预算控制。支持 `--no-lsp` 降级到纯语法分析。
- **`lsp-mcp`**：更轻量的统一 LSP 入口，对接 Rust、TypeScript、Go、Python、Ruby、Java、PHP、C/C++ 等语言服务器，提供定义跳转、引用查询、调用层级、诊断。

**语言覆盖扩展层（覆盖缺口）**：
- **`lsp-tree-sitter`**：定位是“**语言服务器孵化器**”，不是事实提取工具。当遇到 tree-sitter 有语法、但生态中**没有现成 LSP 服务器**的语言或 DSL 时，用它基于该语言的 tree-sitter grammar 快速构建一个轻量级 LSP 适配器，提供基于 AST 模式匹配的符号定义、简单诊断和补全，接入 LSP 增强管道。这让方案的语言覆盖从“被动依赖现有 LSP 生态”转向“**主动按需扩展**”。

**语言覆盖的现实边界**：精确语义（调用图、类型关系）在 **9–13 种主流语言**上可获得 LSP 级或 family-gated 级保障，其余语言只能依赖启发式匹配。这个边界必须在产品中显式标注，不能假装所有语言分析深度相同。

---

### 第三层：分层语义树（可选，供 LLM 导航）

**目标**：如果 LLM 需要在“可导航的业务语义结构”上推理，而不是在扁平调用图上盲目搜索，需要一棵分层语义树。

**参考实现**：
- **`repolect`**：为代码库的**每一个层级节点**（模块、文件、类、函数）生成自底向上的 LLM 摘要，构建语义树；同时维护知识图谱，映射 `CALLS`、`IMPORTS`、`EXTENDS`、`IMPLEMENTS` 关系。查询通过 **LLM 推理在树中导航**，复杂度 O(log N)，而非向量相似度搜索。

**边界**：它的“摘要生成”阶段本身需要 LLM。方案中应**复用它的语义树数据结构和导航逻辑**，但摘要生成交给自己选择的通用 LLM 完成，不绑定它内置的本地模型流程。

---

### 第四层：LLM 语义增强与重构编排（完全解耦）

**目标**：在带证据等级的事实之上，做业务语义解释、重构候选识别、方案提议，并驱动验证闭环。

**流程蓝本直接复用 Unwind 的四段式**，但实现层替换为自选的通用 LLM 编排：

**1. 基于事实的语义摘要（类比 `uw-analyze`）**
LLM 读取 `scan-manifest.json` 或知识图谱的节点/边，为每个函数/模块生成业务语义说明。**每条说明必须锚定到具体的节点 ID**，而不是自由文本。目标是保持 API 契约、业务逻辑和数据模型的准确性。

**2. 结构化审查（类比 `uw-grill`）**
LLM 主动标记**结构事实与业务常识之间的张力**：过时的工作区、无法解释的常量、矛盾之处、死规则、被高频调用但命名模糊的函数、与架构层次不匹配的导入、没有调用者的“死逻辑”。把只有领域专家才能回答的问题写成**问卷**，输出为结构化文档。**这一步直接服务于重构判断**——它不只是还原现状，还在标记“重建会忠实复制但不该复制”的部分。

**3. 重构方案提议（类比 `uw-plan`）**
在事实约束下，LLM 对每个候选提出具体的切断/合并/上移方案，并基于图谱的入度/出度、变更传播路径估计影响面。**每条方案必须引用支撑它的证据边及其等级**，低证据等级的方案标记为“待验证假设”。

**4. 验证闭环（类比 `uw-build` 的差异对比）**
- **结构侧**：重构后重新跑第一、二层工具，用**集合差异**（`scan − docs` 式的集合运算，而非断言）度量结构改善——调用边是否按预期减少、循环依赖是否消除、层次违例是否修复。Archify 的 `compare` 命令也可用于 Before/Delta/After 的结构变更事实输出。
- **行为侧**：用表征测试（`pinion-mcp`、`characterization-test-generator` 的 Jest/pytest/JUnit 模式）锁定原行为；有条件时叠加**差分模糊测试**（研究显示 LLM 重构有 19–35% 在差分测试下功能不等价，仅靠现有测试会系统性高估等价性）。
- **统一闸门**：行为等价 + 结构改善，两者缺一不可。这是现有工具各自为政留下的最大空隙，也是方案中需要自己构建的核心编排逻辑。

**可选补充：因果结构层**
- **`RECoRD`**（学术框架）：多智能体 LLM 将代码逆向工程为**因果关联图**，通过强化微调提升关系抽取准确性（MiniSCOT 上 F1 从 0.69 提升到 0.97）。不提供现成产品，但“因果结构”可作为业务逻辑层的补充表示，用于回答“这个业务决策为什么导致那个下游行为”。

## 组装后的完整数据流

```
源码
  │
  ├─→ [第一层] codebase-memory-mcp (158 语言语法) ──→ SQLite 知识图谱
  │         + Unwind scan-manifest.json (5 语言交叉验证)
  │         + tree-sitter-analyzer (调用图质量校验)
  │
  ├─→ [第二层] code-atlas / lsp-mcp (9–13 语言 LSP 精确增强)
  │         + lsp-tree-sitter (为缺口语言孵化轻量 LSP)
  │
  ├─→ [第三层] repoelect 语义树结构 (自选 LLM 生成摘要)
  │
  └─→ [第四层] 通用 LLM 编排
            ├─ 语义摘要 (锚定节点 ID)
            ├─ 结构化审查 (uw-grill 式问卷)
            ├─ 重构方案提议 (引用证据边 + 等级)
            └─ 验证闭环
                  ├─ 结构侧: 重新扫描 + 集合差异 + Archify compare
                  └─ 行为侧: 表征测试 + 差分模糊测试
                        ↓
                  统一闸门: 行为等价 ∧ 结构改善
```

## 选型矩阵（按优先级取舍）

| 优先级 | 事实层主选 | 语义增强 | 关键理由 |
|---|---|---|---|
| **语言覆盖广度 + 单二进制零依赖** | `codebase-memory-mcp` | 9 种 Hybrid LSP | 158 种语法，SQLite/JSON 均可解耦消费 |
| **调用图跨语言正确性** | `tree-sitter-analyzer` | 13 种完整调用图 | family-gated 防误连，TOON 紧凑输出 |
| **LSP 生态成熟，要精确语义边** | `code-atlas` | 25 种索引，按 LSP 可用性精确 | “LSP-exact + structural floor”设计最清晰 |
| **需要分层语义树供 LLM 导航** | `repolect` 解析层 | 自选 LLM 生成摘要 | 树 + 图双存储，O(log N) 导航 |
| **流程蓝本 + 确定性交叉验证** | `Unwind @unwind/core` | 5 种语言符号级 | `scan → analyze → grill → plan → rebuild → 差异验证` 是最接近目标的编排范式 |
| **缺口语言扩展** | `lsp-tree-sitter` | 按需孵化轻量 LSP | 从“被动依赖生态”转向“主动按需扩展” |

## 需要自己补的核心缺口

**1. 统一验证闸门。** 没有现成工具把“行为等价”和“结构改善”合并成一个通过/拒绝判据。这是方案的核心增量价值所在。

**2. 证据等级的传递与消费逻辑。** 工具产出的边带有等级标记，但 LLM 如何在推理中**按等级加权**、如何在输出中**显式标注假设**，需要自己设计 prompt 结构和输出 schema。

**3. Unwind 流程的“换壳”。** 它的 `scan → analyze → grill → plan → rebuild → 差异验证` 流程逻辑是平台无关的，但实现绑定了 Claude Skills。需要把流程设计和 prompt 结构移植到自选的 LLM 编排层。

**4. 语言覆盖缺口的主动管理。** 对 9–13 种之外的语言，要么接受启发式匹配的低置信度并显式标注，要么用 `lsp-tree-sitter` 按需孵化轻量 LSP。这是一个持续的语言扩展策略，不是一次性配置。

---

## 一句话总结

这套方案的本质是：**用 `codebase-memory-mcp` 做语法广度的基座，用 `code-atlas` / `lsp-mcp` 做语义精度的增强，用 `tree-sitter-analyzer` 做调用图质量校验，用 `Unwind` 的流程逻辑做重构编排蓝本，用 `lsp-tree-sitter` 补语言覆盖缺口，最终把“行为等价 + 结构改善”的统一闸门作为自己构建的核心增量**。所有工具都通过结构化数据（JSON / SQLite / 知识图谱）解耦消费，LLM 的选择完全开放。
