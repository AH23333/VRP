# 构想 v3：定位修正——对标 Archify，面向所有 AI 构建项目

## 1. Archify 实际是什么（源码核验版）

基于本地源码（v3.2.0，MIT，130K+ 安装）核验：

**它是一个"断言验证 + 渲染交付"层，不是分析工具。** 工作流是：agent（Claude/Cursor 等）读仓库 → 手写 typed JSON IR（10 种图：architecture/workflow/sequence/dataflow/lifecycle/erd/class/tree/timeline/waterfall）→ `finalize` 走闸门（schema 校验 ajv、布局规则、真实浏览器 check、原子交付）→ 产出单文件 HTML。

关键事实（决定我们的差异化空间）：

1. **它没有任何代码分析能力**。无 AST、无索引、无 LSP、无事实库。图里每条"事实"（节点、边、ERD 列、类成员）都是 LLM 阅读仓库后的**断言（authored claims）**。
2. **它的闸门验证的是表达质量，不是事实正确性**。schema 一致、布局不重叠、标签不压线、交付原子性——全部通过；"这个组件真的调用那个组件吗"从不在验证范围。
3. **它诚实地声明了这一切**：compare "infers no impact, risk, or merge safety"；reachability "never says blast radius or breakage"；evidence 功能（`SRC n`）只是把 agent 手写的文件/行号钉到一个 git commit，Archify 不验证内容相符。
4. **它的工程质量极高且范式成熟**：typed IR + JSON Schema、原子交付（候选文件通过全部检查后一次 rename，失败保 last-good 字节不变）、结构化修复回执（稳定规则码 + measured evidence + supportedFixes，绝不抛 Node 栈）、全程 fail-closed。
5. **"Claude in the loop is the moat"**：设计评审和失败实验（Mermaid 验证实验）确立的路线——布局判断是产品差异点，明确拒绝 auto-layout（dagre/elk）、Mermaid 解析器、通用图 IR、YAML。

## 2. "比 Archify 更深入"的三个具体含义

| 维度 | Archify | 本项目 | 深度来源 |
|---|---|---|---|
| 事实来源 | **无自有事实**：LLM 断言，仅验证 schema/布局/交付 | 工具确定性提取（AST/LSP/执行） | facts.db + 证据等级 |
| 结论形态 | 描述（图/Delta） | **判据**（通过/拒绝/回滚 + 证据等级） | 事务闸门 |
| 事实范围 | 不验证断言与代码相符 | 结构 + **行为事实**（表征/执行/trace），断言可被工具核验 | freeze pack + 执行车道 |
| 分析对象 | 通用（agent 自己读） | 通用 + **AI 构建病理**作为一等分析对象 | 病理检测器组（第 3 节） |
| 输出密度 | 一张交互图（表达受限） | 证据锚定的 dossier + transaction.yaml + verdict.json | 多视图工件 |
| 闭环 | 止于理解 | 理解 → 事务 → 执行 → 闸门 → 回滚 | 完整管道 |

一句话：**Archify 让 AI 画出"它认为的项目"；我们让工具测出"真实的项目"，并安全地治好它。**

## 3. "vibe = AI 构建"带来的新分析轴：AI 构建病理学

这是差异化核心。AI 构建的项目有可检测的特有病理，现有工具（包括 Archify）都不针对它们：

| # | 病理 | 信号 | 检测器 | 对应重构动作 |
|---|---|---|---|---|
| P1 | 生成接缝：不同会话生成的代码风格互斥 | 同一项目多种错误处理/日志/命名风格 | 模式聚类，按文件统计约定熵 | 统一约定（T1/T4） |
| P2 | 近似重复：AI 倾向重新生成而非复用 | 同一 util 的多个变体散布各文件，命名各异 | 函数级 embedding 聚类 + AST 相似度（变体检测，非精确 copy-paste） | 收敛为单一实现（T1） |
| P3 | 原型残骸 | main2.py / *_old.* / 整段注释掉的旧方案 | 引用图 + 命名启发 + git 形态 | 清理（T2） |
| P4 | 依赖膨胀 | 引库只用一个函数；依赖数/千行比异常 | import 图 vs 实际使用面 | 内联或替换（T2） |
| P5 | 注释-代码错位 | docstring 描述的是旧方案 | LLM 判断注释与实现一致性（语义层任务） | 修注释（T4） |
| P6 | 配置漂移 | .env.example / README 与实际配置项不一致 | 配置项集合 diff | 修文档（T4） |
| P7 | 过度工程与未完成并存 | 单实现接口 + TODO；抽象度方差极大 | 抽象度统计（接口/实现比、层数分布） | 塌缩或补全（T4） |
| P8 | **同义反复测试**：AI 生成的测试照着实现抄 | 断言弱、路径覆盖重复、删实现测试仍可能通过 | **变异测试采样**估计测试套件强度 | 重建测试（T4，闸门前置） |

P8 直接冲击 v2 的降级矩阵："可运行 + 有测试 → 全速车道"不再成立。AI 项目的存量测试**必须先审计再信任**——测试质量审计成为 freeze 阶段的前置步骤。

另一个推论：AI 项目的 git 历史形态（少 commit、大 diff、无意义 message，甚至无历史）意味着**历史考古价值低，病理必须靠当前态检测**。无历史时，行为是唯一硬事实——这反而强化了执行优先（方案 B）的价值。

## 4. 对 v2 结论的翻转与保留

| v2 结论 | v3 处置 | 原因 |
|---|---|---|
| "vibe 项目千行级，增量是过度设计" | **翻转：分档策略** | 面向所有项目后，M/L 档增量必须 |
| "语言广度 ROI 低" | **部分恢复** | 所有项目 = 全语言谱系；但 niche 工具 bus factor 批评仍成立，维持 provider 抽象 |
| "有测试 = 全速车道" | **降级：先审计** | P8 同义反复测试 |
| "vibe 项目大多是 web/req-resp" | **泛化：项目类型分类学** | 见第 5 节 |
| 事务分类学、闸门、canonical ID、解耦、沙箱 | 保留 | 与规模和类型无关 |
| 方案 C（协议优先）的演进路径 | 保留 | 定位修正不改变"工件 + 闸门是持久价值"的判断 |

## 5. 项目类型 × 执行车道矩阵

行为载体因项目类型而异，执行车道（方案 B）需要分型：

| 项目类型 | 行为载体 | 执行车道 | 可自动化程度 |
|---|---|---|---|
| Web/API 服务 | HTTP 请求-响应 | probe + driver（curl/Playwright） | 高 |
| CLI | 命令行调用 | 命令矩阵 driver | 高 |
| 前端应用 | 渲染输出/交互 | 视觉回归 + 组件 harness | 中 |
| 库 (library) | API 表面（导出的输入-输出） | 导出面表征 harness：对每个导出生成调用测试 | 高 |
| 桌面/移动 | UI 事件流 | 无头/截图采样，其余结构车道 | 中低 |
| 游戏/嵌入式 | 难以自动化执行 | 结构车道 + 人工闸门 | 低 |

库是重要补充：没有"入口"，但导出面就是行为边界。Archify 对库只能画依赖图，我们能对导出面做表征冻结。

## 6. 规模分档策略

| 档位 | 规模 | 策略 |
|---|---|---|
| S | < 1 万行 | 全量分析 + 每事务全量重扫（v2 方案照搬，秒级-分钟级） |
| M | 1-50 万行 | 懒分析 + dossier 按需子图 + 事务级局部重扫 |
| L | 50 万行+ / monorepo | 分层进入（先模块级地图再下钻）+ 增量索引必须 |

## 7. 与 Archify 的关系：偷范式、占空位、供事实

### 7.1 可直接移植的工程范式（从它的源码学）

| Archify 范式 | 移植到本项目 |
|---|---|
| typed JSON IR + ajv 强制校验 | facts.db / transaction.yaml / verdict.json 都带 schema_version 和 JSON Schema |
| 原子交付：候选通过全部检查后一次 rename，失败保 last-good 字节不变 | transact 的 commit 语义：闸门全过才落盘，失败回滚到上一个 commit |
| 结构化修复回执：稳定规则码 + measured evidence + supportedFixes，不抛栈 | verdict.json 的失败输出：每条诊断带规则码（如 `gate/behavior-regression`）、实测证据、唯一支持的修复动作 |
| 全程 fail-closed（推断不出就明确说推不出） | 证据等级的核心精神；低置信绝不静默放行 |
| 明确的边界声明（"never says blast radius"） | 我们也要声明：等价性是证据分级不是证明；cold ≠ dead |

它的 Structured Repair Receipt 范式几乎就是 verdict.json 的现成蓝本。

### 7.2 Archify 明确留下的空位（机会地图）

它的 ROADMAP"Not planned"和边界声明里，明确拒绝或留给别人的：

1. **不做代码分析**——事实层整个空着
2. **"Diagram diff UI: better delivered as a companion CLI / CI bot"**——它自己说该由伴生 CLI 做，就是我们
3. **不推断 impact / risk / merge safety**——事务闸门整个空着
4. **不验证 authored claims 与代码相符**——断言核验整个空着（我们的 facts.db 可以做"Archify 图的事实审计器"：把 agent 写的 JSON IR 与工具提取的事实比对，标出无证据支撑的节点/边）
5. **不做 YAML、不做 auto-layout**——与我们无冲突

### 7.3 具体集成路径：给 Archify 供事实

facts.db 可以确定性派生它 10 种图中至少 4 种的**拓扑部分**（不需要 LLM 断言）：

| Archify 图类型 | 从 facts.db 派生 | 来源 |
|---|---|---|
| class | 类/接口/继承/实现/依赖 | 符号表 + 类型边 |
| erd | 表/列/键/外键 | ORM 模型或 SQL DDL 解析 |
| tree | 模块/目录/能力分解 | 文件树 + 分层 |
| architecture | 组件/调用/边界（拓扑） | 调用图 + 分层（布局仍交给 agent，尊重它的"布局是产品"哲学） |

集成形态：`facts.db → typed JSON IR（拓扑 + 证据 ID + SRC n 标注）→ agent 只填布局坐标 → Archify finalize 交付`。效果是"Archify 图，但每个节点/边都有工具级证据"，比它现在的纯断言模式更强。这可以作为我们第一个可发布的楔子（wedge）：**先做"Archify 的事实审计器 + 事实供给器"，再谈重构管道。**

## 8. 修订后的优先级

0. **楔子先行**：给 Archify 做"事实供给器"（facts.db → class/erd/tree/architecture JSON IR）+"事实审计器"（比对 agent 断言与工具事实，标出无证据边）——直接验证 facts.db schema 的价值，且站在 130K+ 安装的生态上获客
1. 测试质量审计（变异测试采样）插入 freeze 前置——AI 项目下它决定一切车道的可信度
2. 病理检测器组从 P2（近似重复）和 P3（原型残骸）起步——检测器最简单、收益最直观
3. 规模分档的 S 档先落地，M 档的懒分析在 C 方案（协议优先）路径上自然获得
4. 项目类型分类学进 precheck 的 capability-manifest——车道选择是它的第一个消费者
