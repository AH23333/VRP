## S3（第四批，2026-11-02）

31. **旧 facts.db 缺新表**：schema 加自有组五表后，已有仓库的 facts.db 不含 annotations/gate_results——validate/gate 直跑即崩 `no such table`。**解法：rw 打开一律 `ensure_schema`（schema 全 IF NOT EXISTS，幂等追加迁移）**。教训：schema 任何变更，所有读写入口都要过 ensure_schema，不能只靠新建库
32. **PowerShell 5.1 嵌套引号**：`\"` 在 PS 双引号串里**不转义**（反引号才转义），`python -c "... COUNT(*) ..."` 里的 `\"` 把串切断、`*` 被 PS 当通配符解析报错。**铁律升级：含 `$`、含嵌套引号、含 `*` 的命令一律落 .py 文件执行，不走 -c 内联**
33. **validate 必须文件为真**：若信任库内 content_hash 快照，文件改了但库没重索引时会误判 active（测试 fixture 故意用假哈希抓出）。正确语义：window 哈希对**仓库文件**重算——窗口变了才 stale；窗口没变再比定义哈希定 cosmetic/active。库只是缓存，文件是唯一真源

## S4（第五批，2026-11-02）

34. **Windows `shell=True` 超时是假的**：`subprocess.run(command, shell=True, timeout=N)` 超时只 kill 直接子进程（cmd.exe），**孙进程（npm/tsc/vitest）还握着 stdout/stderr 管道**——communicate 继续阻塞到孙进程自然退出，30s sleep 命令配 timeout=2 实测跑了 30s。**解法：Popen + 超时 `taskkill /PID <pid> /T /F` 杀整棵进程树**（/T=tree；POSIX 对应 start_new_session=True + killpg）。教训：凡 shell 代理执行（shell=True）的超时都必须按"进程树"语义处理
35. **失败定位要读全 stderr**：freeze E2E 四命令全 rc=1，尾部 `'tsc' is not recognized...` ——第一反应"npm 没找到"是错的（PS 里 npm 解析到 npm.ps1，cmd 子进程走 npm.cmd，两者都在）；真凶是**仓库没装 node_modules，脚本内层的 tsc 不存在**。runtime evidence 的价值就在完整尾部——诊断时先读 payload 全文再下结论

## S5（第六批，2026-11-02）

36. **SQL 视图版本漂移**：`CREATE VIEW IF NOT EXISTS` 不会替换已存在的旧定义——schema 改了视图，旧库查询仍是旧语义（且旧定义可能已坏）。**解法：视图一律 `DROP VIEW IF EXISTS` + `CREATE VIEW`**（视图无数据，重建零成本），表保持 IF NOT EXISTS
37. **"死代码"必须按使用边判，不能按任意入边**：第一版 v_dead_code 用 `NOT EXISTS(任意入边)`，实测 0 命中——CONTAINS/DEFINES 类结构边把每个符号都"救活"了。**正确口径与 s2_deadcode 对齐：仅 CALLS/CALL_REFERENCE/MENTIONS/SPAWNS 计为使用**，加 is_candidate 后滤；对数 134=134 才算过
38. **SQLite DISTINCT 聚合单参限制**：`GROUP_CONCAT(DISTINCT col, '|')` 报 "DISTINCT aggregates must have exactly one argument"——DISTINCT 聚合不可带分隔符，用默认逗号或子查询去重
39. **CBM CLI 输出格式**：get_architecture 默认是人类可读 tree 表（`key: value`+缩进表），不是 JSON——`run_cli` 的 JSON 解析直接失败。须 `--format json`（MCP 参数 format:"json"）；其他工具同理，先探一次真实输出再接管道

## S5 第二批（第七批，2026-11-02）

40. **PageRank 必须闭合图**：facts.db edges 的 dst 可能查无 symbols 行（边引用未落库符号），开图直跑 rank 循环取 `graph[dst]` 即 KeyError。**解法：load_graph 构图时滤掉两端不齐的断边**——图算法前先验证闭合性
41. **code-atlas MCP stdio 细节**：JSON-RPC 按 `\n` 分帧（非 LSP Content-Length 头）；serve 收到请求即用 index.db 应答（后台异步索引不阻塞、数据可能 stale）；stdin 关闭 → server 净退；repo_map 的 `max_tokens` 限 200-20000（默认 2500）。一次性客户端流程：initialize → notifications/initialized → tools/call，按 id 配对响应、跳过 notification 行

## S6（第八批，2026-11-02）

42. **CBM 同名 reindex 会正确剪除已删符号**（正面经验，探针实证 23→21 qns）——G1 重扫可直接用 canonical 名 reindex=True，无需每事务专用 CBM 项目名；但**事务失败后 CBM 缓存停留在事务态**，下次 transact 前的 index 会再次 reindex 拉回，无残留危害
43. **悬垂引用检查绝不能算 CONTAINS/DEFINES 结构边**：文件伪节点（`pkg.calc.py.__file__`）对所有同文件符号有结构边，任意删函数都会被误判"dangling"；只认 CALLS/CALL_REFERENCE/MENTIONS/SPAWNS 使用边（与 v_dead_code #37 同一课）
44. **commit 必须在 facts promote 之后**：git commit → etl promote 改 facts.db → 已跟踪的 facts 变脏 → 下个事务被"树不干净"拒；正确序：_record → promote → verdict → commit（.vrp 被跟踪的仓也干净）
45. **事务回滚只还原编辑文件，不还原闸门副作用**：G3 跑 pytest 会生成 `__pycache__` 等构建产物，若被 add -A 收进提交，回滚后树即脏——repo 卫生（.gitignore 忽略构建产物）是事务执行的前提条件，不是 vrp 的职责

## S6 Second Batch (Ninth Batch, 2026-11-02)

46. **verify_changes explicit file list all marked modified**: passing iles=[...] to code-atlas verify_changes makes it uniformly status:'modified' — the removed-exports check for **deleted files only takes effect when status='deleted'** (verify.js if (!file) branch); in explicit mode, delete files are silently skipped. Workaround: **don't pass files, use git mode** (uncommittedChanges = git diff HEAD staged+unstaged + untracked, respects .gitignore) — the tree is naturally dirty in the applied state after transaction application, deleted files correctly get 'deleted'. Lesson: for MCP tools that accept explicit lists, first check whether they are a lossy mapping of the real git status; when a git snapshot can be obtained, prefer letting the tool fetch it itself
47. **_print_step is multi-line JSON, E2E parsing must not take the last line**: CLI step output is == title == + json.dumps(indent=2) **multi-line**, json.loads(out.splitlines()[-1]) is guaranteed to crash. Correct approach: locate the ==  line, then parse by concatenating all subsequent lines — E2E should first probe the real format before writing parsing code

## Large Repository Wrap-up E2E (Tenth Batch, 2026-11-02)

48. **_fit infinite loop (scale bug, only explodes on the 66K repository)**: _fit's halving loop has two fatal flaws — the reducible set includes len==1 lists (after [:max(1, 1//2)]==[:1], length never changes), and non-list large fields (GROUP_CONCAT giant strings, nested single-element giant lists) don't participate in shrinking; on the small repo the payload always fits into cap and never touches this branch; on tree-sitter-analyzer (dup clusters members 10KB + SCC largest single component 1023 qns) **infinite loop burns 25 minutes** (each round is a pure-CPU json.dumps loop). Fix: reducible set only takes len>1, when exhausted break and accept exceeding soft cap; at the same time, structurally truncate oversized fields at the source (largest becomes {"size":n,"members":[<=30]}, members substr 300). Lesson: **halving loops must prove "strictly decreasing per round"**; scale bugs aren't exposed by unit tests + small-repo E2E, only real large-repository validation exposes them
49. **When timeouts/hangs, suspect budget loops first, not external commands**: the initial 25-minute timeout was attributed to repomix subprocess or MCP watchdog (misjudged direction for half an hour); actually repomix completed in 4s and MCP in 2s. The correct localization method: **staged timing scripts + real-time log flush to disk** (work/dossier_timing.py pattern) — the log's last "start xxx" before the hang is the stuck stage, more reliable than guessing
