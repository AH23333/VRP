# 三方案对比与数据流推演

## 一表对比

| 维度 | A 静态优先 | B 执行优先 | C 最小内核 |
|---|---|---|---|
| 事实来源 | 静态 IR | 动态 trace 优先，静态校正 | 静态 IR（单一 provider） |
| 自建面 | 大（7 阶段） | 最大（A + 沙箱/录制/driver） | 最小（5 命令 2 格式） |
| 首个可用版本速度 | 中 | 慢 | 快 |
| 行为证据强度 | 中（生成表征） | 高（真实执行） | 取决于 freeze 实现 |
| 对消费者 AI 的假设 | 工具内置编排 | 工具内置编排 | AI 主导编排 |
| 适用项目 | 全部 | 可运行的 req/resp 型 | 全部 |
| 死代码判断 | 静态 + 启发式 | trace 校正（最强） | 同 A |

## 数据流推演：同一个 vibe 项目走三遍

样本：Python FastAPI + OpenAI 调用，约 3000 行，无测试，无 git，requirements.txt 缺 2 个依赖，约 30% 是原型期死代码。

**Stage 0（三方案相同）**：无 git → init + commit；识别 FastAPI 入口；发现 .env 有 OPENAI_API_KEY 占位符（无真实值）；发现 requirements.txt；无测试。capability-manifest：`{runnable: unknown, tests: none, secrets: missing-key, git: initialized}`。

**方案 A 走法**：index 30 秒；LSP（basedpyright）装上，产出 lsp-exact 边；freeze 阶段尝试运行——缺依赖，安装失败 2 个 → LLM 生成 T3 修复事务（补 requirements + 修 import），标记非等价 → 运行成功但启动即因 API key 报错 → 降级"可启动不可出网"车道：表征测试对无外部调用的路由生成成功，OpenAI 路径用合成 mock；dossier 报告行为证据覆盖约 60%，死代码候选 41 个（heuristic 级）；T1/T2 事务跑通，删除冷路径代码时闸门要求扩展表征覆盖，部分拒绝。
**结论：跑得通。关键卡点是密钥与表征覆盖率的循环依赖（想删的代码恰好测不到）。**

**方案 B 走法**：probe 直接撞缺依赖 → 报错栈 → T3 循环 2 轮 → 启动成功（OpenAI 路由 500，其余 200）→ driver 生成 curl 序列 20 条 + Playwright 冒烟 3 条 → 流量录制，OpenAI 外呼被 record/replay 层拦截为合成响应 → trace 校正：30% 疑似死代码中 26% 确认 cold（trace + 静态双证据），4% 静态疑死但 driver 未覆盖，显式列出不可自动删；harness 固化后 T1/T2 全速通过。
**结论：跑得通且证据质量明显更高。工程成本集中在 B3 录制层；driver 未覆盖路径是系统性盲区，必须显式暴露而非静默放过。**

**方案 C 走法**：precheck / index / dossier 各就位；freeze 命令内部走 A 的降级逻辑，产出 60% 覆盖的 freeze pack；编排交给消费者 AI：它读 dossier 提出混合草案 → CLI 强制拆分为 9 个单类型事务 → 7 个过闸，2 个 T4 等人工确认。
**结论：跑得通，最快拿到端到端闭环。质量方差来自消费者 AI，闸门兜住了危险部分。**

## 对上一轮评审的自我修正

1. **增量分析从"缺失"降级为"后期优化"**：vibe 项目千行级，每事务全量重扫秒级，v1 做增量是过度设计。
2. **"行为冻结前置于重构提议"仍成立，但发现更深的问题**：等价性对 vibe 项目常常根本无定义（项目跑不起来时）。由此引出事务分类学——T3/T4 不是等价重构的例外处理，而是主要诉求。
3. **上一轮低估了秘密/外部 API 问题**：vibe 项目的典型核心就是调 LLM API，没有密钥就没有行为。record/replay mock 层不是可选项，是数据流能否闭环的枢纽。

## 三方案共同的、之前未列出的问题（头脑风暴新增）

- **grill 阻塞问题**：v1 的 grill 问卷假设有人回答。"面向通用 AI"意味着工具不能假设能对话。三方案统一改为：问卷默认 AI 自答 + 置信度标注，人工参与是增强而非依赖。
- **图匹配问题**：重构前后如何对齐节点。不做图同构（不可行），改用事务声明（declared_moves）作为匹配提示，未声明差异视为回归。
- **验证的元问题**：不验证"生成的表征测试本身是否有效"的管道，会在自己制造的假证据上通过闸门。eval 集（拿已知等价/不等价的重构对测试闸门的假阳性率）是三方案共同的欠账。

## 决策建议

- **演进路径**：C 先行（最快验证工件 schema 与闸门价值）→ 把 A 的降级矩阵和事务分类学做进 C 的命令实现 → B 的 probe/trace 作为新命令加入，只对可运行项目开启。三方案共享 facts.db schema 与 transaction.yaml，不存在推倒重来。
- **现在就该定的三件事**：① facts.db schema 与 canonical ID 规则；② 事务类型枚举与闸门矩阵；③ 沙箱选型（Docker 优先）。
- **最大不确定性**：表征测试 / driver 自动生成的质量。建议先拿 10 个真实 vibe 项目做手工推演，量出生成成功率，再定自动化程度。

## 未解决问题清单

- 等价闸门假阳性率的度量方法（eval 集如何构造）
