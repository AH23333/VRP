# 构想 v4：端到端工程数据流与工具接口

本文档回答三个前版未回答的问题：完整数据流长什么样、每个流程用哪些现有工具、每个工具的接口要怎么改才能把数据流打通。

## 0. 范围裁定（对 v2/v3 的收敛）

- **不按项目类型分车道**（v3 §5 作废）。通用化靠"命令发现"：precheck 探测项目实际存在的命令（build/test/typecheck/lint），下游闸门只消费命令，不做类型假设。web/游戏/嵌入式/库走同一管道，差异只体现在发现的命令集合和语言分层。
- **方案 B 的 driver/流量录制移出核心**，降级为后续增强。核心管道的行为证据 = 发现到的测试命令 + 变异测试采样。
- **事实纪律不变**：AI 只能引用证据，不能创造证据。

## 1. 端到端数据流总图

```
项目源码
  │
  ▼
[S0 precheck] git 初始化/快照 + 构建/测试/lint 命令发现 + 密钥探测
  │   └─→ .vibe-pipe/capability-manifest.json
  ▼
[S1 提取] 非AI工具组按语言分层提取（详见 §3）
  │   ├─ Provider: tree-sitter（语法地板，全语言）
  │   ├─ Provider: scip-* 索引器（编译器级精确，按语言）
  │   ├─ Provider: LSP 批处理驱动（无 scip 的语言）
  │   └─ Provider: universal-ctags（残余语言符号地板）
  │   └─→ .vibe-pipe/extracts/*.json（原始产物缓存）
  ▼
[S2 病理检测] 非AI检测器组（ast-grep / jscpd / 清单解析）
  │   └─→ findings（P1-P8，锚定节点 ID）
  ▼
[S3 规范化] canonical ID 铸造 + 边合并 + 证据分级 + 锚点校验
  │   └─→ .vibe-pipe/facts.db
  ▼
[S4 freeze] 测试质量审计（变异采样）+ 测试命令基线
  │   └─→ .vibe-pipe/freeze/{test-audit,behavior}.json
  ▼
[S5 dossier 生成] 按 token 预算出视图：模块地图/函数卡片/病理清单/问题问卷
  │   └─→ .vibe-pipe/dossier/
  ▼
[AI 层] 通用 AI 读 dossier → 产出三类受校验工件
  │   ├─ annotation.json  （业务语义，锚定节点 ID，引用证据边）
  │   ├─ structure.json   （整合后的完整项目结构：模块/分层/职责/规则提议）
  │   └─ transactions/*.yaml（重构事务批次）
  │   ※ 全部经 JSON Schema + 锚点存在性校验，不合格退回修复回执
  ▼
[S6 架构规则固化] AI 提议的分层 → 生成为各语言依赖规则工具的配置 → 工具执行
  │   └─ 违例清单 = 重构目标（AI 理解，工具执法）
  ▼
[S7 重构循环] 逐事务：应用编辑 → 增量重提取 → 五道闸门 → commit/revert
  │   └─→ transactions/tx-NNNN.yaml + verdict-NNNN.json
  ▼
[S8 交付] 合并事务分支 + 终版 dossier + structure.json
      + Archify 图（class/erd/tree/architecture，从 facts.db 派生）
      + verdict 历史 + 未决 T4 人工确认清单
```

## 2. 规范数据模型（facts.db）

```sql
-- schema_version = 1，所有 AI 工件同理（仿 Archify 的版本纪律）
nodes(
  id TEXT PRIMARY KEY,          -- sha256(relpath + qualname)[:16]
  kind TEXT,                    -- file/module/class/function/method/field
  lang TEXT,
  path TEXT, start INT, end INT,
  qualname TEXT, content_hash TEXT
);
edges(
  src TEXT, dst TEXT,
  kind TEXT,                    -- contains/imports/calls/references/extends/implements
  evidence TEXT,                -- index-exact > lsp-exact > family-gated > heuristic
  provider TEXT,                -- 来源 provider，可追溯
  PRIMARY KEY(src, dst, kind, provider)
);
edge_votes(src, dst, kind, provider, evidence);  -- provider 分歧留档，离线审计用
findings(id, pathology TEXT, node_ids TEXT, detail JSON);  -- P1-P8 检测结果
annotations(
  node_id TEXT, payload JSON,
  citations TEXT,               -- 必须引用已存在的边/节点
  created_by TEXT, verified INT DEFAULT 0
);
```

**合并策略**：边身份 = (src, dst, kind)。多 provider 对同一条边各自投票，取证据等级最高者，分歧进 `edge_votes`。**AI 注解永远不产生边、不改 evidence**——只能引用。

**ID 稳定性**：移动文件/改名通过事务的 `declared_moves` 维护 `id_map(old→new)` 映射表；闸门按声明核验，未声明差异视为回归（沿用 v2 结论，不做图同构）。

## 3. 阶段 × 工具组 × 接口改造

### S0 precheck（自建 + git）

| 工具 | 原生接口 | 改造 | 产出 |
|---|---|---|---|
| git | CLI | 无 init→首 commit→事务分支；每事务一 commit | 版本基础 + 回滚机制 |
| 构建文件嗅探 | 读 package.json / pyproject / Cargo.toml / go.mod / pom / CMakeLists / Makefile | 自建：发现并提取 **命令**（build/test/lint/typecheck），不猜类型 | capability-manifest.json |
| 密钥探测 | 读 .env* | 自建：发现密钥缺失项，标记后续 mock 需求 | 同上 |

### S1 提取（核心：按语言分层选 provider，adapter 统一落库）

| 层 | 工具（现实存在） | 原生输出 | 接口改造 | 证据等级 |
|---|---|---|---|---|
| 精确层 | scip-typescript / scip-python / scip-java / scip-ruby / scip-kotlin（Sourcegraph SCIP 索引器，每语言一个 CLI） | SCIP protobuf（定义+引用+调用，基于真实编译） | 适配器：protobuf→JSON→canonical 边；occurrence 行号→字节偏移换算 | index-exact |
| 精确层（无 scip 的语言） | LSP 批处理 harness（自建，约 500-800 行）：驱动 rust-analyzer / clangd / gopls / OmniSharp / jdtls | LSP 协议（definition/references/references 深度） | 自建：didOpen 全项目→逐符号请求→去重→落库 | lsp-exact |
| 结构层（全语言地板） | tree-sitter（直接用 bindings+grammars，或包一层 codebase-memory-mcp 作 provider 之一） | AST / 符号 / contains 边 | 适配器：AST→nodes(contains/定义位置)；调用表达式→candidate call 边 | 定义位置 exact；call 边 heuristic |
| 符号层（残余语言） | universal-ctags `--output-format=json` | 符号清单（50+ 语言） | 适配器：直接映射 nodes | heuristic |

**语言分层决策表**（进 capability-manifest，S1 据此选 provider 组合）：

| 语言 | 精确层 | 结构层 |
|---|---|---|
| TS/JS/Python/Java/Kotlin/Ruby | scip-* | tree-sitter |
| Rust/C/C++/C#/Go | LSP harness | tree-sitter |
| 其余 | —（无精确层，显式标注） | tree-sitter + ctags |

**打通关键**：所有 provider 实现同一个 `Provider` 接口（`extract(paths) → RawFacts`），适配器职责 = 原生格式 → nodes/edges 行 + 证据等级 + provider 标记。原始产物缓存在 `extracts/`，规范化失败可重放。

### S2 病理检测（非AI检测器，锚定节点 ID）

| 病理 | 工具 | 原生输出 | 改造 |
|---|---|---|---|
| P1 风格接缝 | ast-grep（YAML 规则，`--json`） | 结构模式匹配结果 | 写规则集：错误处理/日志/命名模式按文件聚类，熵超阈值出 finding |
| P2 近似重复 | jscpd（JSON reporter，多语言） | 克隆簇 | 簇→node_ids 组，finding type=P2 |
| P3 原型残骸 | ast-grep + 命名启发 | 匹配结果 | `*_old/*_v2/main2` 规则 + 引用图交叉（无入边才升级 finding） |
| P4 依赖膨胀 | 清单解析（自建：各语言 lockfile/manifest） | 依赖清单 | import 图 vs 声明依赖 diff |
| P8 同义反复测试 | Stryker（JS/TS/C#）/ mutmut（Python） | mutation score | 采样模式：只跑 30 分钟预算内的变异子集，估算套件强度 |

### S3 规范化（自建核心，工作量最集中）

ID 铸造、边合并（§2）、锚点校验、`extracts/` 缓存重放、增量接口：`extract(changed_files_only)` → 边手术（删旧边→加新边）。

### S5/S6 AI 层与架构规则（AI 理解 → 工具执法）

AI 的 `structure.json` 提议分层（如 `services 不得 import routes`）。管道把它**编译成各语言依赖规则工具的配置**并执行：

| 语言 | 执法工具 | 配置生成 |
|---|---|---|
| JS/TS | dependency-cruiser | 生成 `.dependency-cruiser.cjs` 规则 |
| Python | import-linter | 生成 `importlinter` 契约 |
| Java | ArchUnit | 生成测试类 |

违例清单 = 重构目标。**这一步是"AI 理解整合业务逻辑"的落地点：AI 的理解被翻译成机器可执行的规则，然后由非AI工具验证与执法。**

### S7 五道闸门（全部消费"发现的命令"，与项目类型无关）

| 闸门 | 内容 | 项目无对应命令时 |
|---|---|---|
| G1 语法门 | 增量重提取成功，无新 parse 失败 | 恒可执行 |
| G2 静态检查门 | typecheck/lint 命令通过（tsc --noEmit / mypy / cargo check…，由 precheck 发现） | 跳过并标注 |
| G3 测试门 | 测试命令通过（行为证据） | 跳过并降级 verdict 置信度 |
| G4 声明门 | declared_moves 与实际 diff 一致；difftastic 生成结构 diff 报告 | 恒可执行 |
| G5 改善门 | 事务针对的 finding 计数单调下降 | 恒可执行 |

事务类型 T1-T4 沿用 v2 的闸门矩阵。G2 是关键设计：**"装了 tsc 就跑 tsc"是配置驱动而非类型驱动**，这就是通用性的实现方式。

## 4. AI 工件契约（接口打通的另一半）

AI 的三个输出都是受校验文档，校验失败退回 Archify 式结构化修复回执（规则码 + 位置 + 支持的修复动作）：

1. **annotation.json**：锚点校验（node_id 必须存在）、引用校验（citations 必须指向已存在的边）、不产生边、不改证据。
2. **structure.json**：模块边界必须切成 facts.db 中存在的节点集合；分层提议编译为 §3-S6 的规则配置。
3. **transactions/*.yaml**：schema 校验 + 单类型强制（混合草案自动拆分）+ declared_moves 的端点存在性预检。

**数据流方向纪律**：AI 只读 dossier、只写三类工件。AI 永远不直接写 facts.db——写入只有一个入口（S3 校验器），这是数据流能保证一致性的根本。

## 5. 重构循环（S7 细节）

```
取一个事务 tx-NNNN
  → git commit（事务边界）
  → 应用 edits
  → 增量重提取（仅变更文件）
  → G1-G5 依序执行，首败即停
  → 全过: id_map 登记换位，产出 verdict-NNNN.json（含证据）
  → 有败: git revert，verdict 记录失败规则码与修复建议，事务退回 AI
循环至事务批次耗尽 → S8
```

## 6. 最终交付物

给用户的是一个**完整重构后的项目**（合并的事务分支上的工作树）+ 可审计的证据包：

1. 重构后的项目目录（git 历史 = 事务历史，可回放）
2. `structure.json`——AI 整合业务逻辑后的完整项目结构（模块/职责/分层/规则）
3. Archify 图（class/erd/tree/architecture 从 facts.db 确定性派生，见构想v3 §7.3）
4. verdict 历史全集（每个事务的证据与判定）
5. 未决 T4 人工确认清单
6. 测试质量审计报告（mutation 采样）

## 7. 组件构建顺序（依赖链）

1. facts.db schema + 三个契约文件的 JSON Schema（一切的地基）
2. precheck + tree-sitter + ctags provider（**全语言地板第一天就可用**）
3. dossier builder + annotation 校验（AI 回路打通）
4. 事务引擎 + G1/G4（结构级重构闭环，无需测试也能跑）
5. scip-*/LSP providers（精度升级，按语言逐个接入）
6. 病理检测器 + G5（ast-grep/jscpd 规则集）
7. 变异审计 + G3 深化 + 依赖规则生成器（S6）
8. Archify 集成（§6-3）

每步都可独立交付验证，第 4 步完成时即有端到端闭环（结构级重构）。

## 8. 需验证的外部事实（开工前核对清单）

- scip-* 各语言索引器的成熟度与输出完整性（尤其 Kotlin/Ruby）
- jscpd 对"变体式重复"（非逐字拷贝）的召回率——不满足则 P2 需要补 embedding 聚类
- LSP harness 对大型仓库的批处理耗时（rust-analyzer/clangd 冷启动成本）
- Stryker/mutmut 的采样模式是否原生支持预算限制（不支持则自建子集选择）
- codebase-memory-mcp 等 v1 提及工具的实际输出 schema（决定 provider 接入成本）
